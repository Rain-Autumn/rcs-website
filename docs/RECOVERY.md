# RCS website recovery procedure

This runbook covers recovery of the public RCS website. It deliberately contains no credentials,
password hashes or private publication data.

## Recovery sources

Keep three independent recovery sources:

1. the reviewed source and deployment history in GitHub;
2. the immutable standalone release artifacts and attestations generated by GitHub Actions;
3. encrypted backups of private runtime state stored outside the VPS.

The production server keeps application releases under
`/var/www/raijucloudsystem.com/releases/`. The active release is selected by the
`/var/www/raijucloudsystem.com/current` symbolic link. Private state is separate:

- `/etc/rcs/rcs.env` contains the production environment;
- `/var/lib/rcs/research-publications` contains Research publication state;
- `/var/lib/rcs/team-members` contains Team directory state.

Never print those files in CI output or copy them into this repository.

## Backup requirements

- Encrypt private backups before they leave the VPS.
- Keep at least one copy outside OVH and outside GitHub.
- Protect access with a separate account and multifactor authentication.
- Record backup time, size and checksum without recording secret values.
- Test restoration quarterly using an isolated host or directory.

A safe inventory check records metadata only:

```bash
sudo stat --format='%n %s bytes %y' \
  /etc/rcs/rcs.env \
  /var/lib/rcs/research-publications \
  /var/lib/rcs/team-members
```

## Rebuild from a reviewed release

1. Identify the last trusted commit and successful `main` workflow run.
2. Download its `rcs-release-<sha>` artifact and SBOM from GitHub Actions.
3. Verify its GitHub attestation before transfer:

   ```bash
   gh attestation verify rcs-release.tar.gz --repo Rain-Autumn/rcs-website
   ```

4. Recreate the restricted `rcsdeploy` account using the reviewed scripts in `deploy/`.
5. Restore `/etc/rcs/rcs.env` and the two private data directories from an encrypted backup.
6. Deploy the verified release through the restricted deployment command.
7. Validate Nginx, systemd and the public routes.

The bootstrap and deploy scripts are references tied to the current Debian architecture. Review
paths, ownership and service names before using them on a replacement server.

## Roll back an unhealthy release

The deployment helper performs an automatic rollback when its local health check fails. For a
manual incident response, first inspect rather than mutate:

```bash
readlink -f /var/www/raijucloudsystem.com/current
find /var/www/raijucloudsystem.com/releases \
  -mindepth 1 -maxdepth 1 -type d -printf='%T@ %f\n' | sort -rn
sudo systemctl status raiju-site.service --no-pager
```

Select only a previously trusted 40-character commit directory. Change the active symlink and
restart the service through a reviewed administrative procedure; never delete the current or old
release during the incident.

## Validation checklist

```bash
sudo nginx -t
sudo systemctl is-active --quiet raiju-site.service
curl --fail --silent --show-error https://raijucloudsystem.com/fr >/dev/null
curl --fail --silent --show-error https://raijucloudsystem.com/en >/dev/null
curl --fail --silent --show-error https://raijucloudsystem.com/nl >/dev/null
```

Confirm that Research and Team private data are readable by the service without disclosing their
contents. Document the incident, the chosen release SHA, checksums, validation results and any
credential rotations.
